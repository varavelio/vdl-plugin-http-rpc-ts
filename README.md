This plugin generates HTTP RPC code only.

Data models come from [`varavelio/vdl-plugin-ts`](https://github.com/varavelio/vdl-plugin-ts): Generate types first, then point this plugin at them.

## Quick Start

1. Generate TypeScript models with `varavelio/vdl-plugin-ts`.
2. Generate RPC client (`target "client"`) and/or RPC server (`target "server"`).
3. Run your normal VDL generation command (for example: `vdl generate`).

```vdl
const config = {
  version 1
  plugins [
    {
      src "varavelio/vdl-plugin-ts@<version>" // Use a version from plugin releases
      schema "./schema.vdl"
      outDir "./generated/types"
      options {
        importExtension "js"
      }
    }
    {
      src "varavelio/vdl-plugin-http-rpc-ts@<version>" // Use a version from plugin releases
      schema "./schema.vdl"
      outDir "./generated/client"
      options {
        target "client"
        typesImport "../types/index.js"
        importExtension "js"
      }
    }
    {
      src "varavelio/vdl-plugin-http-rpc-ts@<version>" // Use a version from plugin releases
      schema "./schema.vdl"
      outDir "./generated/server"
      options {
        target "server"
        typesImport "../types/index.js"
        importExtension "js"
      }
    }
  ]
}
```

If you only need one side, keep only one RPC plugin block.

## Plugin Options

| Option            | Type                     | Required | Default | What it changes                                                                                       |
| ----------------- | ------------------------ | -------- | ------- | ----------------------------------------------------------------------------------------------------- |
| `typesImport`     | `string`                 | yes      | -       | Import path pointing to the output generated by `varavelio/vdl-plugin-ts` (used exactly as provided). |
| `target`          | `"client" \| "server"`   | yes      | -       | Selects what to generate in that invocation. The plugin generates one target at a time.               |
| `importExtension` | `"none" \| "js" \| "ts"` | no       | `"js"`  | Controls internal imports between generated RPC files. It does not rewrite `typesImport`.             |

## Generated Files

For `target "client"`:

- `client.ts`

For `target "server"`:

- `server.ts`
- `adapters/node.ts`
- `adapters/fetch.ts`

If your schema has no discovered `@httpRpc` or `@proc` annotations, no files are emitted.

## What You Get

For `target "client"`:

- `NewClient(baseURL).build()` to create a typed client.
- Flattened procedure builders under `client.procs.*()`.
- Global and proc-level headers (static or dynamic providers).
- Interceptors with typed `inputAs<T>()` input access.
- Retry/timeout for procedures.
- Bounded response bodies (`withMaxResponseBodyBytes`, 4 MiB default).

For `target "server"`:

- `new Server<Props>()` with typed request context.
- Typed registration APIs for procedures.
- Middleware at global, RPC, and procedure levels with typed `inputAs<T>()` input access.
- Global and RPC-level error handlers (sanitized `Internal error` by default).
- Bounded request bodies (`setMaxRequestBodyBytes`, 4 MiB default).
- `createNodeHandler(...)` and `createFetchHandler(...)` adapters for HTTP runtimes.
- Global and RPC-level error handlers.
- `createNodeHandler(...)` and `createFetchHandler(...)` adapters for HTTP runtimes.

Both targets include runtime catalogs:

- `VDLPaths` (VPP-2 `lowerFirst(rpcName)` routes)
- `VDLProcs` (each entry carries `rpcName`, `rpcRoute`, `name`, `path`, `hasInput`, `hasOutput`)

Non-marker annotations are preserved in procedure metadata and cloned per
request, so middleware cannot leak state across requests. Service-level
annotations never propagate to procedures. Handler contexts expose
`rpcRoute` and `path` alongside `rpcName` and `procName`.

## RPC Annotation Model

This plugin follows the VDL annotation model:

- `@httpRpc` marks a top-level type as an HTTP RPC service.
- `@proc` marks a field as a request-response procedure.

```vdl
@httpRpc
type Messages {
  @proc
  send {
    input {
      roomId string
      text string
    }

    output {
      accepted bool
    }
  }

}
```

## Usage Example

### Client

```ts
import { NewClient } from "./generated/client/client";

const client = NewClient("http://localhost:3000/rpc")
  .withGlobalHeader("authorization", "Bearer <token>")
  .build();

const procOutput = await client.procs.messagesSend().execute({
  roomId: "room-1",
  text: "hello",
});

console.log(procOutput.accepted);
```

### Server (Node.js adapter)

```ts
import { createServer } from "node:http";
import { Server } from "./generated/server/server";
import { createNodeHandler } from "./generated/server/adapters/node";

type Context = { requestId: string };

const rpcServer = new Server<Context>();

rpcServer.rpcs
  .messages()
  .procs.send()
  .handle(async (_ctx) => {
    return { accepted: true };
  });

const handler = createNodeHandler(rpcServer, () => ({ requestId: "req-1" }), {
  prefix: "/rpc",
});

createServer(async (req, res) => {
  await handler(req, res);
}).listen(3000);
```

### Server (Fetch-compatible adapter)

```ts
import { Server } from "./generated/server/server";
import { createFetchHandler } from "./generated/server/adapters/fetch";

const rpcServer = new Server();

export default {
  fetch: createFetchHandler(rpcServer, undefined, { prefix: "/rpc" }),
};
```

## Adapter Behavior

- Mount adapters under the RPC base path; segments below the mount point must be `/{rpc}/{procedure}` using the VPP-2 `lowerFirst` transport form.
- Only `POST` requests route to procedures (anything else gets `405` with an `Allow: POST` header). Paths without exactly two segments get `404`.
- Unknown procedures keep the standard `ok:false` envelope behavior.
- See [SECURITY.md](SECURITY.md) for request/response size limits and error privacy guarantees.

## Important Notes

- `baseURL` in `NewClient(baseURL)` should point to your RPC prefix (for example: `https://api.example.com/rpc`).
- The generated client appends `/{lowerFirst(rpcName)}/{procName}` automatically following VPP-2.
- `typesImport` must point to the generated output from `vdl-plugin-ts`.
- To generate both client and server, run this plugin twice (one block per `target`).
